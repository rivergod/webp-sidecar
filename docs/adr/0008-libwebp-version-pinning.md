# 0008. libwebp 버전 고정: 최신 릴리스 태그(v1.6.0)를 쓰고 main의 미릴리스 수정을 추적한다

- 상태: proposed
- 날짜: 2026-10-23
- 결정자: -
- 관련 문서: [docs/research/0003-server-language-rust-vs-go.md](../research/0003-server-language-rust-vs-go.md) "libwebp 최신 안정판", [ADR-0002](0002-server-language.md)

## 맥락

설계 제약은 "libwebp 버전을 서버 빌드에서 명시적으로 고정하고 최신 안정판을 쓴다"이다([goals-and-constraints.md](../design/goals-and-constraints.md)). 조사 중 이 제약과 충돌하는 사실이 나왔다(확인 2026-10-23).

- 최신 릴리스는 1.6.0이다(NEWS 2025-06-30, 태그 커밋 `4fa21912`). 이후 릴리스는 없다.
- main은 v1.6.0보다 362커밋 앞서 있고, 이 프로젝트가 쓸 코드 경로의 수정을 포함한다. 보안 영향과 CVE 배정 여부는 미확인이다.
  - `d29e00aa` anim_decode `ZeroFillFrameRect` 오버플로 (**디코딩 경로, 신뢰할 수 없는 입력**)
  - `1844042d` VP8 디코더의 잘못된 비트스트림 처리 (**디코딩 경로**)
  - `ace1fa52` row × stride 포인터 오프셋 32비트 overflow (dec/enc/dsp)
  - `44b94d53`, `652631be` anim_encode 오류 경로 double-free (인코딩 경로)
  - `6391cf3f` `WebPMuxSetCanvasSize` signed overflow (mux)
- `libwebp-sys`(ADR-0002의 Rust 추천안)는 v1.6.0 태그를 벤더링한다. 커밋을 고정하려면 포크하거나 자체 `-sys`가 필요하다.
- 1.3.2 이후 libwebp 자체에 배정된 CVE는 NVD에서 찾지 못했다.

## 결정 동인

1. 알려진 결함이 신뢰할 수 없는 입력 경로(디코딩)에 남지 않아야 한다.
2. 버전이 명확해야 한다. `GetInfo`가 보고하는 버전이 실제 코드와 일치해야 한다.
3. 프로토타입에 맞는 단순함.
4. 서버 프로세스 격리(ADR-0001)가 1차 방어선이라는 점.

## 검토한 선택지

1. **최신 릴리스 태그(v1.6.0) 고정 + main 수정 추적 목록 유지**
2. main의 특정 커밋 고정
3. v1.6.0 + 선별 패치(cherry-pick) 적용

## 결정

**프로토타입 단계에서는 선택지 1을 추천한다.**

- 서버는 v1.6.0(태그 커밋 `4fa21912338357f89e4fd51cf2368325b59e9bd9`, tarball sha256 `e4ab7009bf0629fd11982d4c2aa83964cf244cffba7347ecd39019a9e38c4564`)으로 빌드한다.
- 위 미릴리스 수정 목록을 research/0003에 유지하고, 새 릴리스가 나오면 올린다.
- 이유: 프로토타입은 가설 검증이 목적이고, 디코딩은 격리된 하드닝 컨테이너 안에서 일어난다. 태그 버전은 `GetInfo`의 버전 문자열과 정확히 일치한다(main 커밋은 다음 릴리스 전까지 버전 매크로가 1.6.0으로 남아 있어 구분되지 않을 가능성이 높다 — 추정). `libwebp-sys`를 그대로 쓸 수 있다.
- **제품화를 검토하는 시점(Phase 5 회고)에는 다시 결정한다.** 그때까지 새 릴리스가 없으면 선택지 3(디코딩 경로 수정만 선별 패치)을 우선 검토한다.

### 결과

- 긍정: 빌드가 단순하고, 버전 보고가 정확하고, 바인딩을 그대로 쓴다.
- 부정: 디코딩 경로의 알려진 미릴리스 수정(`d29e00aa`, `1844042d`, `ace1fa52`)이 빠진 상태로 신뢰할 수 없는 입력을 처리한다. 영향은 미확인이며 컨테이너 격리로 완화한다.
- 부정: 추적 목록을 사람이 갱신해야 한다.

### 확인 방법

- Phase 1: `GetInfo`가 `1.6.0`을 보고하고, 빌드에 쓴 libwebp 소스가 태그 커밋과 일치한다(`libwebp-sys`면 벤더 서브모듈 포인터 `4fa21912`, 자체 빌드면 tarball sha256).
- Phase 5: 퍼저를 위 수정 대상 경로(anim_decode, VP8 디코더)에 집중해 돌리고 결과를 회고 ADR에 반영한다.

## 선택지별 장단점

### 1. 릴리스 태그 고정 (추천)

- 장점: 단순, 버전 명확, `libwebp-sys` 그대로 사용.
- 단점: 미릴리스 수정 누락.

### 2. main 커밋 고정

- 장점: 알려진 수정을 모두 포함한다.
- 단점: 릴리스 품질 보증이 없는 중간 상태다. 버전 문자열이 실제 코드와 다르다. Rust에서는 자체 `-sys` 또는 포크가 필요하다.

### 3. 태그 + 선별 패치

- 장점: 릴리스 기준을 유지하면서 위험한 경로만 고친다.
- 단점: 패치 선별·적용·검증을 직접 해야 한다. 자체 빌드가 필요하다. 버전 문자열에 패치 표시를 따로 해야 한다.
