# 0016. 메모리 예산 기반 요청 허용: 작업별 추정 메모리를 예산에서 예약한다

- 상태: proposed
- 날짜: 2026-10-23
- 결정자: -
- 관련 문서: [ADR-0012](0012-server-runtime-config.md), [docs/research/0007-server-memory-budget.md](../research/0007-server-memory-budget.md)

## 맥락

ADR-0012는 기본값 조합(메모리 1 GiB, 동시 처리 2, `max_pixels` 8192²)에서 OOM이 나면 기본값 조정을 새 ADR로 제안하라고 했다. 측정 결과는 다음과 같다([research/0007](../research/0007-server-memory-budget.md)).

- 디코딩: 8192² 두 개를 동시에 처리해도 최고 661 MiB로 안전하다.
- 인코딩: 8192² 하나만으로도 OOM이다(단독 2.0–2.3 GiB). 4096²도 두 개를 동시에 처리하면 OOM이다.
- 픽셀당 메모리가 작업마다 7배쯤 다르다(디코딩 약 5 B/px, 인코딩 약 31–36 B/px). 메모리의 대부분은 libwebp 인코더 자체다.

동시 처리 수 하나로는 이 차이를 반영할 수 없다. 서버가 OOM으로 죽으면 처리 중인 모든 요청이 실패한다.

## 결정 동인

1. 기본 설정에서 상한 안의 어떤 요청 조합도 서버를 OOM으로 죽이지 않아야 한다.
2. 상한 안의 큰 디코딩(8K 이미지 등)은 계속 받아야 한다.
3. 설정과 구현이 단순해야 한다.

## 검토한 선택지

1. **메모리 예산 기반 허용**: 요청마다 추정 메모리를 계산해 예산(설정값)에서 예약하고, 예약할 수 없으면 기다린다. 혼자서도 예산을 넘는 요청은 즉시 `RESOURCE_EXHAUSTED`로 거부한다.
2. 인코딩 전용 픽셀 상한(`max_encode_pixels`)을 추가하고 동시 처리 수는 유지한다.
3. 기본 메모리 제한을 올린다(예: 4 GiB, 동시 처리 1).
4. 기본값을 유지하고 OOM 위험을 문서화한다.

## 결정

**선택지 1을 추천한다.**

- 새 설정 `max_memory_bytes`(환경변수 `WEBP_SERVER_MAX_MEMORY_BYTES`): 동시에 진행 중인 요청들이 예약할 수 있는 메모리 합계. 기본값은 컨테이너 기본 제한 1 GiB의 75%인 768 MiB.
- 추정식(측정값에 여유를 둔 값, research/0007):
  - 정지 이미지 디코딩: 입력 크기 + 6 B × 픽셀 수
  - 애니메이션 디코딩: 입력 크기 + 10 B × 캔버스 픽셀 수(캔버스 버퍼 2개 + 전송 버퍼, Phase 3에서 측정해 조정)
  - 인코딩: 40 B × 픽셀 수(입력 버퍼 포함)
  - GetFeatures: 입력 크기
- 혼자서도 `max_memory_bytes`를 넘는 요청은 기다리지 않고 바로 `RESOURCE_EXHAUSTED`로 거부한다. 메시지에 추정치와 예산을 적는다.
- `max_concurrency`는 CPU 사용 상한으로 그대로 둔다(두 제한을 모두 만족해야 처리한다).
- 기본값으로는 인코딩 최대 크기가 약 4096²(768 MiB ÷ 40 B ≈ 2,000만 픽셀)로 사실상 제한된다. 더 큰 인코딩이 필요하면 컨테이너 메모리와 `max_memory_bytes`를 함께 올린다.

### 결과

- 긍정: 상한 안에서는 요청 조합과 무관하게 메모리 합계가 예산 아래로 유지된다(추정식이 맞는 한).
- 긍정: 큰 디코딩은 그대로 받고, 작은 요청은 큰 요청과 함께 처리된다.
- 부정: 추정식은 측정 기반 근사다. libwebp 버전이나 인코더 설정이 바뀌면 다시 재야 한다.
- 부정: 설정이 하나 늘고, `GetInfo`의 `Limits`에도 노출하려면 proto 필드를 추가해야 한다(하위 호환 변경).
- 부정: 기본 설정에서 8192² 인코딩은 거부된다(지금도 OOM으로 실패하므로 동작이 나빠지지는 않는다).

### 확인 방법

- `server/scripts/measure-memory.sh 1g 2 8192`와 `1g 2 4096`에서 OOM이 0이고, 예산을 넘는 요청은 `RESOURCE_EXHAUSTED`로 거부된다.
- Phase 3에서 애니메이션 작업의 계수를 측정해 갱신한다.

## 선택지별 장단점

### 1. 메모리 예산 기반 허용 (추천)

- 장점: 작업 종류별 차이를 반영해 OOM을 막는다. 설정 하나로 컨테이너 메모리와 맞출 수 있다.
- 단점: 추정식 유지가 필요하다. 구현이 조금 늘어난다(가중치 세마포어).

### 2. 인코딩 전용 픽셀 상한

- 장점: 이해하기 쉽다.
- 단점: 동시 처리 수 × 작업별 최대치로 계산해야 해서 상한이 보수적으로 작아진다. 애니메이션처럼 계수가 다른 작업이 늘 때마다 상한이 늘어난다.

### 3. 기본 메모리 제한 상향

- 장점: 코드 변경이 없다.
- 단점: 4 GiB에서도 8192² 인코딩 두 개는 OOM이다. 사이드카 하나에 큰 메모리를 고정으로 잡는다.

### 4. 유지 + 문서화

- 장점: 아무것도 바꾸지 않는다.
- 단점: 상한 안의 정상 요청으로 서버가 죽을 수 있다.
