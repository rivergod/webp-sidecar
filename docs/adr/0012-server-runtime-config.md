# 0012. 서버 실행 구성: 이름, 설정, 상한 기본값, 동시 처리, 컨테이너, 소켓

- 상태: accepted. "이미지 / libc" 항목만 superseded by [0021](0021-glibc-distroless-image.md)(2026-11-03)
- 날짜: 2026-10-23
- 결정자: Ilkang Na
- 관련 문서: [ADR-0002](0002-server-language.md), [ADR-0003](0003-transport.md), [docs/design/grpc-api.md](../design/grpc-api.md) §3, [docs/research/0006-license.md](../research/0006-license.md)

## 맥락

Phase 1 서버를 만들기 전에 실행 구성의 기본값이 필요하다. 상한은 코드에 고정하지 않고 설정값으로 관리하기로 했다([grpc-api.md §3](../design/grpc-api.md)). 설정 키 표는 설계 문서에 두고, 이 ADR은 방식과 기본값을 정한다.

## 결정 동인

1. 컨테이너(사이드카) 배포에 맞는 설정 방식.
2. 메모리 사용을 예측할 수 있어야 한다(컨테이너 메모리 제한 안에서 동작).
3. 격리 강화(작은 이미지, 네트워크 없음, 파일 권한으로 접근 제어).
4. 단순함.

## 검토한 선택지

- 설정: **환경변수 + 명령줄 인자** / 설정 파일(TOML 등) / 셋 다
- 동시 처리: **blocking 스레드 풀 + 동시 처리 수 상한** / 요청마다 무제한 / 별도 워커 프로세스
- 이미지: **musl 정적 + scratch** / glibc 동적 + distroless/cc
- TCP: **기본 꺼짐** / 기본 켜짐

## 결정

| 항목 | 결정 |
|---|---|
| 이름 | 크레이트·바이너리·컨테이너 이미지 모두 `webp-imageio-server` |
| 설정 방식 | 환경변수와 명령줄 인자로 같은 키를 받는다. 우선순위는 명령줄 인자 → 환경변수 → 기본값. 환경변수 접두사는 `WEBP_SERVER_`. 설정 파일은 두지 않는다. 키 표는 [grpc-api.md §3](../design/grpc-api.md) |
| 상한 기본값 | 입력 64 MiB / 캔버스 8192 × 8192 픽셀(67,108,864) / 1,000프레임 / 메타데이터 2 MiB / 조각 1 MiB. 측정 후 조정한다 |
| 동시 처리 | libwebp 호출은 비동기 런타임 스레드가 아니라 blocking 스레드 풀에서 실행한다. 동시에 libwebp 작업을 하는 요청 수를 `max_concurrency`(설정값, 기본 **2**)로 제한한다. 슬롯이 없으면 기다리고, 기다리는 시간의 상한은 클라이언트 데드라인이다 |
| 컨테이너 기본 제한 | 메모리 1 GiB, CPU 2 (`deploy/`의 compose 기본값) |
| 이미지 / libc | musl 정적 바이너리 + `scratch`. glibc는 정적 링크하지 않는다([research/0006](../research/0006-license.md)) |
| UDS | 기본 경로 `/run/webp-imageio/webp.sock`. 서버와 클라이언트만 마운트하는 전용 볼륨에 둔다. 소켓 파일 모드 기본 `0660`, 두 컨테이너가 같은 그룹을 쓴다 |
| TCP | 기본 꺼짐. 켜면 주소를 지정해야 하고 예시·권장값은 `127.0.0.1:50051` |

### 결과

- 긍정: 컨테이너 환경변수만으로 설정하고, 같은 키를 명령줄에서도 쓸 수 있다.
- 긍정: 동시 처리 수 상한으로 메모리 사용의 상한을 계산할 수 있다.
- 긍정: 이미지가 작고(스파이크 기준 0.42 MB) libc 라이선스 문제가 없다.
- 부정 — **메모리 예산 위험**: libwebp `WebPAnimDecoder`는 캔버스 크기 RGBA 버퍼를 2개 잡는다(libwebp v1.6.0 `src/demux/anim_decode.c` 137–141행, 확인 2026-10-23). 기본 상한(8192²)의 캔버스 버퍼 하나는 256 MiB이므로 애니메이션 디코딩 요청 하나가 512 MiB 이상을 쓴다. 동시 2개면 입력 버퍼까지 더해 기본 메모리 제한 1 GiB를 넘을 수 있다. 인코딩, 특히 `WebPAnimEncoder` 쪽은 더 많이 쓸 수 있다(추정). Phase 1에서 최악 입력으로 측정하고, OOM이 나면 기본값(메모리 제한, `max_concurrency`, `max_pixels`) 조정을 새 ADR로 제안한다.
- 부정: musl 기본 메모리 할당기는 멀티스레드에서 느릴 수 있다(추정). Phase 4에서 확인한다.
- 부정: 설정 파일이 없으므로 키가 많아지면 관리가 불편해질 수 있다.

### 확인 방법

- Phase 1: 모든 키가 명령줄 인자와 환경변수로 동작하고 우선순위가 맞다(단위 테스트).
- Phase 1: 기본값 조합(메모리 1 GiB, CPU 2, 동시 2)에서 상한 직전 크기의 정지 이미지·애니메이션 디코딩과 인코딩을 동시에 돌려 OOM이 나지 않는다.
- Phase 1: 컨테이너가 `scratch` 이미지, non-root, read-only 루트 파일시스템, 네트워크 없음으로 실행되고 UDS로 호출된다.

## 선택지별 장단점

### 설정 방식

- 환경변수 + 명령줄 인자(채택): 컨테이너 친화적이고 단순하다. 키가 많아지면 불편하다.
- 설정 파일: 구조화된 설정에 좋지만 read-only FS에서 파일을 마운트해야 하고 파서가 늘어난다.

### 동시 처리

- blocking 풀 + 상한(채택): libwebp 호출이 CPU를 오래 쓰는 동기 함수라 비동기 런타임 스레드를 막지 않게 한다. 메모리 상한 계산이 가능하다.
- 무제한: 큰 요청이 몰리면 메모리가 예측 불가능하다.
- 워커 프로세스: 요청 단위 크래시 격리를 얻지만 복잡하다. Phase 5 회고에서 필요하면 검토한다.

### 이미지 / libc

- musl + scratch(채택): 가장 작고 시스템 콜 표면이 작다. 할당기 성능은 확인이 필요하다.
- glibc + distroless/cc: 할당기 성능 우려가 적지만 이미지가 크다(스파이크 기준 11 MB).
