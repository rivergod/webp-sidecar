# 0018. 정지 이미지 디코딩 출력 버퍼 재사용(버퍼 풀)과 만료 정책

- 상태: accepted
- 날짜: 2026-10-29
- 결정자: Ilkang Na
- 관련 문서: [ADR-0012](0012-server-runtime-config.md)(서버 설정, musl 정적 + scratch), [ADR-0016](0016-memory-budget-admission.md)(메모리 예산, proposed), [docs/research/0009-benchmark-results.md](../research/0009-benchmark-results.md), [docs/roadmap.md](../roadmap.md) Phase 5-2

## 맥락

Phase 4 비용 분해에서 서버 안 libwebp 디코딩이 가장 컸다. 같은 코드를 glibc로 빌드하면 빨라졌다(M lossy 3.34 → 2.82 ms). 서버는 musl 정적 바이너리다(ADR-0012). musl 할당자는 큰 블록을 매번 mmap/munmap한다. 그래서 요청마다 새 출력 버퍼의 페이지 폴트와 커널의 0 채우기가 생긴다고 추정했다.

Phase 5-2에서 같은 세션에 잰 서버 안 디코딩 시간(musl, CPU 12 고정, 50회 중앙값, ms):

| 입력(photo) | 새 버퍼, 0 채우기 생략 | 같은 버퍼 재사용 | 차이 |
|---|---|---|---|
| lossy M (1024×768) | 3.20 | 2.75 | −14% |
| lossy L (1920×1080) | 7.73 | 6.36 | −18% |
| lossy XL (4000×3000) | 46.1 | 36.4 | −21% |
| alpha XL | 81.6 | 72.7 | −11% |
| lossless XL | 183.3 | 175.2 | −4% |

- 재사용은 이전에 잰 glibc 빌드(M lossy 2.82, XL lossy 50.7)보다도 빠르다. 값은 다른 날의 측정이라 참고로만 본다.
- 효과는 큰 이미지에서 가장 크다(XL 출력 버퍼 48 MB).
- 0 채우기 생략은 이미 반영했다(`decode_still_rgba_into`). 위 표의 왼쪽 열이 그 상태다.

## 결정 동인

1. Phase 5-2 목표: ADR-0011 대 JNI 50% 미달 조건(사진 lossy·alpha)을 줄인다.
2. 서버 이미지와 배포 형태(ADR-0012: musl 정적, scratch)를 바꾸지 않는 쪽이 낫다.
3. 재사용 때문에 메모리가 무한정 붙잡혀 있으면 안 된다. 부하가 끝나면 상주 메모리가 돌아와야 한다.
4. 이전 요청의 픽셀이 다른 요청의 응답에 섞이면 안 된다.

## 검토한 선택지

1. **출력 버퍼 풀**: 용량 상한과 유휴 만료를 둔 서버 안 재사용
2. glibc 기반 이미지(예: distroless/cc): ADR-0012를 대체하는 새 ADR이 필요하고 이미지가 커진다
3. musl + 다른 할당자(mimalloc 등)로 C의 `malloc`까지 바꾼다. 정적 바이너리에서 libwebp의 `malloc`까지 바뀌는지는 미확인이다
4. 그대로 둔다

## 결정

**선택지 1을 추천한다.**

| 항목 | 정책 |
|---|---|
| 대상 | Decode RPC의 정지 이미지 출력 버퍼만. 애니메이션 캔버스는 libwebp(`WebPAnimDecoder`) 내부 버퍼라 제외한다 |
| 총량 상한 | `buffer_pool_bytes`(`--buffer-pool-bytes` / `WEBP_SERVER_BUFFER_POOL_BYTES`), 기본 128 MiB. XL 버퍼(48 MB) 두 개와 여유이고, 동시 처리 기본값 2와 맞춘다. 0이면 풀을 끈다 |
| 버퍼 하나의 상한 | 따로 두지 않는다(총량 이하면 재사용). 효과가 가장 큰 쪽이 큰 버퍼라서다. 총량보다 큰 버퍼는 보관하지 않는다 |
| 꺼내기 | 필요한 크기 이상인 버퍼 중 가장 작은 것. 없으면 새로 만든다 |
| 돌려놓기 | 응답 전송이 끝나 마지막 조각이 해제될 때(`Bytes::from_owner`). 총량을 넘으면 가장 오래 쓰지 않은 버퍼부터 버린다 |
| 유휴 만료 | `buffer_pool_idle_ms`(`--buffer-pool-idle-ms` / `WEBP_SERVER_BUFFER_POOL_IDLE_MS`), 기본 30,000 ms. 마지막으로 돌아온 뒤 이 시간이 지난 버퍼는 주기 정리(만료 시간의 절반 간격)로 해제한다. 부하가 끝나면 상주 메모리가 돌아온다 |
| 메모리 예산 | 풀 용량은 상주 메모리다. ADR-0016을 채택하면 예산에서 풀 총량 상한을 먼저 빼고, 예약할 수 없을 때는 풀을 먼저 비운 뒤 다시 시도한다 |
| 정보 노출 방지 | 디코딩은 기존 내용을 지운 뒤 시작하고(길이 0), 성공했을 때만 출력 길이를 설정한다. libwebp는 성공하면 출력 영역 전체를 쓴다. 실패한 요청은 픽셀을 보내지 않는다 |

### 결과

- 긍정: 서버 안 디코딩이 큰 이미지에서 11–21%(lossy·alpha) 빨라진다. 배포 형태는 그대로다.
- 부정: 유휴 상태에서도 최대 128 MiB(기본)를 30초 동안 붙잡는다. 컨테이너 기본 메모리 1 GiB 기준으로 디코딩 최고치(8192² 두 개 동시, 661 MiB, research/0007)에 더해도 1 GiB 안이다.
- 부정: 설정이 둘 늘고, 서버에 동시성 있는 공유 상태(풀)가 생긴다.

### 확인 방법

- 단위 테스트:
  - 꺼내기는 가장 작은 충분한 버퍼를 고르고, 총량을 넘으면 오래된 것을 버린다.
  - 유휴 만료가 지나면 비운다. 0이면 풀이 꺼진다.
- 정보 노출 테스트: 큰 이미지를 디코딩한 버퍼로 손상 입력을 디코딩하면 실패하고 빈 버퍼다. 이어서 작은 이미지를 디코딩하면 새 버퍼로 디코딩한 결과와 같다.
- 서버 통합 테스트와 샘플 기대값(RGBA 해시)이 그대로 통과한다.
- 성능: Phase 5-2 재판정 측정에 포함한다. 풀이 있는 빌드와 없는 빌드를 같은 묶음에서 잰다.
- 메모리: 부하 후 유휴 만료 시간이 지나면 컨테이너 메모리 사용량이 기준선으로 돌아온다.

## 선택지별 장단점

### 1. 버퍼 풀 (추천)

- 장점: 측정한 효과가 가장 크다(glibc보다도 크다). 배포 형태를 바꾸지 않는다.
- 단점: 설정과 공유 상태가 늘고, 유휴 메모리를 붙잡는다(상한과 만료로 묶는다).

### 2. glibc 기반 이미지

- 장점: 코드 변경이 없다. libwebp 내부 할당도 함께 빨라진다.
- 단점: ADR-0012(scratch, 정적)를 바꿔야 한다. 이미지와 공격 표면이 커진다. 측정 효과가 풀보다 작다.

### 3. musl + 다른 할당자

- 장점: 배포 형태를 유지하면서 모든 할당이 빨라질 수 있다.
- 단점: C 쪽까지 바뀌는지 미확인이다. 의존성과 라이선스 검토가 늘어난다.

### 4. 그대로

- 장점: 할 일이 없다.
- 단점: 측정한 개선을 버린다.
