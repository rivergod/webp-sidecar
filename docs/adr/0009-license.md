# 0009. 프로젝트 라이선스: Apache-2.0

- 상태: proposed
- 날짜: 2026-10-23
- 결정자: -
- 관련 문서: [docs/research/0006-license.md](../research/0006-license.md), [LICENSE](../../LICENSE)

## 맥락

저장소에는 아직 라이선스가 없다(`LICENSE`는 자리만 있다). 배포물은 세 가지다: libwebp를 정적 링크한 서버 컨테이너 이미지, ImageIO 플러그인 jar, 문서. 의존성 라이선스는 MIT, Apache-2.0, BSD-3-Clause 계열이고, 벤치 전용 JMH만 GPL-2.0 + Classpath Exception이다([research/0006](../research/0006-license.md)). 주 사용처는 Spring 애플리케이션이다.

## 결정 동인

1. 모든 의존성과 호환돼야 한다.
2. 플러그인을 쓰는 애플리케이션(대부분 기업 내부 서비스)에 추가 의무를 지우지 않아야 한다.
3. 이미지 코덱 분야라 특허 관련 조항이 있으면 좋다.
4. 저장소 전체(서버, 클라이언트, proto, 문서, 자체 생성 샘플)에 하나의 라이선스를 쓰면 관리가 쉽다.

## 검토한 선택지

1. **Apache-2.0**
2. MIT OR Apache-2.0 (이중)
3. MIT
4. BSD-3-Clause
5. copyleft 계열(MPL-2.0, LGPL, GPL-3.0)
6. 라이선스 없이 비공개 유지

## 결정

**선택지 1(Apache-2.0)을 추천한다.** 저장소 전체에 적용한다. 단, 제3자 내용(karpathy 발췌, `samples/third_party/`)은 각자의 라이선스를 따른다.

함께 할 일:

- `LICENSE`를 Apache-2.0 전문으로 바꾼다.
- `NOTICE`에 프로젝트 저작권 줄을 쓴다. 저작권자(개인/조직)는 사람이 정한다.
- Phase 1에서 서버 이미지용 제3자 고지 생성과 의존성 라이선스 허용 목록 검사를 빌드에 넣는다.
- glibc를 정적 링크하지 않는다. 벤치 산출물은 배포하지 않는다.

### 결과

- 긍정: 클라이언트 쪽 주요 의존성(grpc-java, Netty, Guava)과 같은 라이선스다. 기업 사용자가 익숙하고 허용 목록에 대개 들어 있다.
- 긍정: 명시적 특허 허여와 특허 소송 시 종료 조항이 있다.
- 부정: MIT보다 길고, 수정한 파일에 변경 사실을 표시하는 등 조건이 조금 더 있다.
- 부정: GPLv2 전용 프로젝트에는 이 코드를 넣을 수 없다(이 프로젝트의 사용처와는 무관).
- 부정: Rust 생태계 관례(`MIT OR Apache-2.0`)와 다르다. 서버 크레이트를 crates.io에 공개할 계획이 생기면 다시 본다.

### 확인 방법

- `LICENSE`, `NOTICE`가 저장소 루트에 있고 README가 라이선스를 밝힌다.
- Phase 1: 서버 이미지 안에 제3자 고지 파일이 있고, 의존성 라이선스 검사가 빌드에서 통과한다.

## 선택지별 장단점

### 1. Apache-2.0 (추천)

- 장점: 특허 조항, 클라이언트 의존성과 일치, 기업 친화적.
- 단점: MIT보다 조건이 많다.

### 2. MIT OR Apache-2.0

- 장점: Rust 생태계 관례. 사용자가 둘 중 하나를 고를 수 있다.
- 단점: 라이선스 파일 두 개를 관리한다. Java 사용자에게는 이점이 거의 없다.

### 3. MIT

- 장점: 가장 짧고 단순하다.
- 단점: 특허 조항이 없다.

### 4. BSD-3-Clause

- 장점: libwebp, protobuf와 같은 라이선스다.
- 단점: 특허 조항이 없다.

### 5. copyleft 계열

- 장점: 수정본 공개를 강제할 수 있다.
- 단점: 플러그인 사용자에게 의무가 생긴다. GPL-2.0-only는 Apache-2.0 의존성과 호환되지 않아 불가능하다. 이 프로젝트의 목적(교체하기 쉬운 ImageIO 플러그인)과 맞지 않는다.

### 6. 비공개 유지

- 장점: 제품화 판단(Phase 5) 전까지 선택지를 열어 둔다.
- 단점: 외부 기여와 공개 벤치마크 검증이 어렵다. 나중에 라이선스를 정할 때 그때까지의 기여자 동의가 필요할 수 있다.
