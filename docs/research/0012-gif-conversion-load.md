- 관련: [ADR-0016](../adr/0016-memory-budget-admission.md)(메모리 예산, proposed), [ADR-0017](../adr/0017-output-volume-limits.md)(작업량 상한, proposed), [ADR-0012](../adr/0012-server-runtime-config.md)(서버 상한과 동시 처리), [design/grpc-api.md](../design/grpc-api.md) §2.5

## 요약

- **동시 부하에서 교착을 발견해 고쳤다.**
  - 증상: 한 클라이언트가 서버 동시 처리 수(2)보다 많은 변환을 같은 연결로 보내면 모두 멈췄다. 동시 4건 이상이 lossy·lossless 모두 성공 0건이었고, 전부 데드라인 초과였다.
  - 원인: 슬롯을 기다리는 요청의 미수신 데이터가 HTTP/2 연결 수신 창을 막았다.
  - 수정: 서버 HTTP/2 창 크기 관계를 바꿨다(`fix/server-h2-flow-control`, [design/grpc-api.md](../design/grpc-api.md) §2.5). 수정 뒤에는 동시 16건까지 처리량이 슬롯 2개의 한계에서 일정하게 유지된다.
- **메모리는 이 작업의 제약이 아니다.**
  - 영상 같은 GIF(약 500×300, 100프레임 안팎) 변환의 서버 메모리 최고치는 10–59 MiB(단건)다. 동시 16건에서도 75 MiB다.
  - 프레임 수에 비례해 늘긴 한다. 480×270 lossless 1,000프레임이 153 MiB다.
- **제약은 CPU 시간과 대기다.**
  - 서버 하나(CPU 2, 동시 2)의 처리량은 사용자 GIF 기준 lossy 약 1.2건/초, lossless 약 0.6건/초다.
  - 대기 길이에 상한이 없어 동시 요청이 늘면 지연이 비례해 는다.
  - 대기를 포함한 지연이 클라이언트 데드라인(30초)을 넘으면 거의 끝난 작업도 취소된다. 이때 처리량 자체가 떨어진다: 합성 GIF lossless 동시 16건에서 0.46 → 0.28건/초, 44건 중 20건 실패.
- **사이드카 경로의 효율은 libwebp `gif2webp` CLI와 비슷하다.** 출력 크기는 거의 같고, 시간은 lossy가 비슷하고 lossless가 더 빠르다.
- **사용법 주의**: JDK GIF 리더는 프레임 원본(바뀌지 않은 픽셀이 투명)을 돌려준다. 이 플러그인 writer에 넘기기 전에 앱이 disposal을 적용해 캔버스에 합성해야 한다(`GifFrames`가 참고 구현).

## 단건 변환 (서버 새로 시작, 기본 제한, 데드라인 10분)

시간은 GIF 디코딩과 합성(클라이언트), 그리고 인코딩(writer → 서버 EncodeAnimation)이다. 메모리는 서버 컨테이너 cgroup `memory.peak`다.

| 파일 | 모드 | 합성 ms | 인코딩 ms | WebP 크기 | GIF 대비 | 서버 최고 MiB |
|---|---|---|---|---|---|---|
| dn0t5cpw | lossy | 300 | 1,796 | 2.89 MB | 0.30 | 15 |
| dn0t5cpw | lossless | 271 | 3,529 | 7.56 MB | 0.78 | 27 |
| image_50k6r1c7 | lossy | 163 | 1,155 | 1.59 MB | 0.35 | 12 |
| image_50k6r1c7 | lossless | 166 | 2,526 | 5.30 MB | 1.16 | 21 |
| 480×270 × 10 | lossy / lossless | 70 / 69 | 340 / 573 | 0.07 / 0.43 MB | 0.14 / 0.85 | 10 / 43 |
| 480×270 × 100 | lossy / lossless | 193 / 199 | 1,116 / 4,009 | 0.97 / 4.87 MB | 0.16 / 0.82 | 11 / 48 |
| 480×270 × 300 | lossy / lossless | 440 / 443 | 2,866 / 11,816 | 3.09 / 15.0 MB | 0.17 / 0.81 | 14 / 59 |
| 480×270 × 1,000 | lossy / lossless | 1,180 / 1,188 | 8,969 / 39,999 | 9.66 / 50.1 MB | 0.16 / 0.82 | 34 / 153 |

- **시간**은 프레임 수에 거의 비례한다.
  - lossy는 캔버스 픽셀 × 프레임 100만 개당 약 70–95 ms다.
  - lossless는 약 180–310 ms다.
  - 480×270 lossless 1,000프레임(40초)은 클라이언트 기본 데드라인 30초를 넘는다.
- **메모리**는 캔버스 몫에 프레임 수 몫이 더해진다. 100 → 1,000프레임으로 늘 때 증가분은 다음과 같다.
  - lossy: 23 MiB, 픽셀·프레임당 약 0.2 B
  - lossless: 105 MiB, 약 0.9 B
  - 인코더가 프레임별 압축 결과를 끝까지 모아 두고, 마지막에 하나로 조립하기 때문으로 본다(추정, libwebp `WebPAnimEncoder`).
- **lossless는 GIF보다 커질 수 있다**(image_50k6r1c7: 1.16배). 원본이 128색 팔레트라 GIF가 이미 효율적이고, 합성한 트루컬러 프레임을 인코딩하기 때문이다. 영상 같은 GIF의 변환은 lossy가 맞다(GIF 대비 0.14–0.35).

## 동시 부하 (서버 하나: 메모리 1 GiB, CPU 2, 동시 처리 2, 클라이언트 기본 데드라인 30초, 단계당 60초)

같은 GIF를 동시 N개 스레드가 반복 변환한다. 합성은 미리 한 번 한다(서버 부하를 본다). 클라이언트는 JVM 하나, 채널(연결) 하나다.

| lossless 처리량 | 0.30/s | 0.57/s | **0** (8건) | **0** (16건) | **0** (32건) |

|---|---|---|---|---|---|---|
| lossy | 1 / 2 / 4 / 8 / 16 | 0.74 / 1.42 / 1.42 / 1.44 / 1.42/s | 실패 0 | 1.4 / 1.4 / 2.8 / 5.5 / 11.2 s | 1.4 – 11.5 s | 13 – 28 |

- **처리량**은 동시 2건에서 한계에 닿는다(슬롯 2개, CPU 2). 그 이상은 대기만 늘고, 지연은 동시 수에 비례한다.
- **데드라인 초과는 대기 때문이다.** 지연 ≈ (동시 수 / 2) × 1건 시간이다.
  - 이것이 30초를 넘으면 늦게 슬롯을 잡은 요청이 일을 하다 취소된다.
  - 그 만큼 서버 CPU를 버려서 처리량이 0.46 → 0.28건/초로 떨어졌다(과부하 붕괴).
  - 지금 서버에는 대기 길이나 대기 시간 상한이 없다.
- **메모리**는 동시 16건에서도 최고 75 MiB로, 기본 제한 1 GiB와 거리가 멀다.

## 교착: 원인과 수정

| 항목 | 내용 |
|---|---|
| 조건 | 한 HTTP/2 연결에서 동시 요청 수 > 서버 동시 처리 수, 그리고 대기 요청들이 보낸 데이터 ≥ 연결 수신 창 |
| 원인 | 서버는 슬롯을 잡은 뒤에야 입력을 읽는다. 대기 요청의 미수신 데이터가 연결 창을 차지해 슬롯을 가진 요청도 더 보내지 못한다. hyper 기본값은 연결 창 = 스트림 창 = 1 MiB라 대기 요청 하나(프레임 하나 720 KB 이상)로 충분했다 |
| 영향 범위 | 업로드가 큰 RPC 전부(애니메이션·정지 인코딩, 큰 lossless 디코딩). Phase 4 벤치는 단일 스레드라 드러나지 않았다 |
| 수정 | 스트림 창 256 KiB, 연결당 최대 동시 스트림 64, 연결 창 32 MiB. 불변식 `연결 창 ≥ 2 × 최대 스트림 × 스트림 창`(컴파일 시점 검사) |
| 확인 | 재현 테스트 `server/tests/flow_control.rs`(슬롯 1개, 4 MiB 업로드 3개, 수정 전 60초 제한, 수정 후 1.7초). 업로드 처리량 변화 없음(인코딩 M·XL, 측정 오차 안). 응답 방향은 `FlowControlIntegrationTest`로 문제없음을 확인 |

## ADR-0016, 0017에 주는 근거

| 질문 | 측정 결과 | 반영 |
|---|---|---|
| 애니메이션 인코딩 메모리가 프레임 수와 함께 느는가 | 는다. lossy 약 0.2 B, lossless 약 0.9 B / 픽셀·프레임(캔버스 몫 위에) | ADR-0016 추정식에 프레임 몫을 더한다(프레임을 받을 때마다 예약) |
| 영상 같은 GIF 대량 변환에서 메모리가 문제인가 | 아니다(동시 16건 최고 75 MiB) | 메모리 예산은 큰 캔버스(4096² 이상) 방어가 주 목적이다 |
| 인코딩 쪽 작업량 상한이 필요한가 | 시간은 캔버스 × 프레임에 비례한다(lossless 100만 px당 약 0.2–0.3 s). 572×315는 상한(2^30)에 닿으려면 프레임이 5,959개여야 해서 `max_frames`가 먼저 걸린다 | ADR-0017의 합성 픽셀 상한을 EncodeAnimation(캔버스 × 받은 프레임 수)에도 적용한다. 큰 캔버스의 긴 애니메이션을 결정적으로 거부한다 |
| 서버 쪽 대기 제어가 필요한가 | 필요하다. 상한 없는 대기가 데드라인 초과와 처리량 붕괴를 만들었다 | ADR-0017에 대기 상한(대기 요청 수)을 더한다. 넘으면 즉시 `RESOURCE_EXHAUSTED`를 내서 클라이언트가 물러서게 한다 |
| 요청 시간 상한 60초가 맞는가 | 단건 최장(480×270 lossless 1,000프레임)이 40초다. 슬롯을 잡은 뒤부터 재므로 대기는 포함하지 않는다 | 60초 유지 |

## 한계

- 서버 하나, 클라이언트 JVM 하나(연결 하나)로 쟀다. 여러 클라이언트, 여러 연결은 재지 않았다(교착 수정의 논리는 연결마다 성립한다).
- 부하 단계는 60초씩이다. 장시간 안정성과 메모리 단편화는 보지 않았다.
- 사용자 GIF 두 개의 출처와 라이선스를 모르므로 저장소에 넣지 않았다. 재현에는 같은 구조의 합성 GIF를 쓴다.
- 합성 GIF는 "바뀌지 않은 픽셀 = 투명" 최적화가 없고 인터레이스다. 서버 작업량은 같지만 클라이언트 GIF 디코딩 비용은 다를 수 있다.
