# 커밋, 브랜치, 병합

이 저장소에서 git을 쓰는 방식이다(결정자 지시, 2026-10-23). 원격 저장소와 CI는 첫 배포 때 정한다([roadmap.md](../roadmap.md) "첫 배포 전 결정"). 원격이 생기면 push와 리뷰 규칙을 이 문서에 보탠다.

## 브랜치

- `main`은 항상 빌드와 테스트가 통과하는 상태로 둔다. `main`에 직접 커밋하지 않는다.
- 작업은 `main`에서 브랜치를 만들어 한다. 이름은 `<type>/<짧은-설명>`이다. type은 커밋 type과 같다.
  - 예: `feat/phase-4-bench`, `docs/git-workflow`, `fix/decode-pixel-limit`
- 브랜치 하나에는 한 가지 목적(로드맵 단계 하나, 결정 하나, 버그 하나)만 담는다.

## 커밋

- 논리 단위로 나눠 커밋한다. 작업이 길면 **주요 항목이 끝날 때마다** 커밋한다(한 단계를 커밋 하나로 몰지 않는다).
- 커밋 하나에 관련 없는 변경을 섞지 않는다. 설계를 바꾸는 코드는 해당 문서·ADR과 같은 커밋이나 그 앞 커밋에 둔다.
- 메시지 첫 줄은 `<type>: <요약>`이다. 범위를 밝히려면 `<type>(<범위>): <요약>`으로 쓴다(예: `feat(server): ...`).
  - type: `feat`, `fix`, `docs`, `test`, `build`, `chore`, `refactor`
  - 요약은 한국어로 써도 된다. 본문에는 무엇보다 **왜**를 쓴다.
- 커밋 전에 바꾼 모듈의 검사를 돌린다(명령: [AGENTS.md](../../AGENTS.md) "빌드 / 테스트 / 린트 명령"). 통과하지 못한 상태로 커밋해야 하면 본문에 그 사실과 이유를 적는다.
- 커밋하지 않는 것: 빌드 산출물, 받아 쓰는 대용량 입력(벤치 세트, 공식 테스트 벡터), 비밀값. `.gitignore`로 막는다.

## 병합

- 브랜치는 `main`에 **`git merge --no-ff <브랜치>`**로 병합한다. fast-forward 병합을 하지 않는다. 병합 커밋이 작업 단위의 경계를 남긴다.
- 병합 커밋 메시지는 git 기본 첫 줄(`Merge branch '<브랜치>'`)을 유지하고, 본문에 그 브랜치에서 한 일을 몇 줄로 요약한다.
- 병합 전에 브랜치에서 바꾼 모듈의 검사가 통과해야 한다.
- 병합한 브랜치는 지운다(`git branch -d <브랜치>`).
- 공유된(push한) 브랜치는 rebase하지 않는다. 로컬에만 있는 브랜치는 병합 전에 `main` 위로 rebase해도 된다.

## 에이전트

- 사람이 요청하지 않으면 push하지 않는다(원격이 아직 없다).
- 브랜치 생성, 커밋, `--no-ff` 병합은 작업 지시 범위 안에서 에이전트가 해도 된다. 되돌리기 어려운 작업(`reset --hard`, 강제 push, 브랜치 삭제 전 미병합 커밋 버리기)은 사람에게 먼저 확인한다.
